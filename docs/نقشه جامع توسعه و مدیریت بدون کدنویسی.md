## 26.22 Version-Aware Learning / دانش وابسته به نسخه

> هر آموزش یا knowledge item باید علاوه بر «موضوع»، مشخص کند مربوط به کدام نسخه، release، API revision، framework version یا وضعیت زمانی است. هدف این است که My-AI بداند یک روش فقط در نسخه 1 معتبر بوده، در نسخه 2 جایگزین شده، deprecated شده یا همچنان معتبر است.

- [ ] ثبت version/release در metadata هر منبع، lesson و knowledge item.
- [ ] ثبت بازه اعتبار زمانی (valid_from / valid_until) برای دانش در صورت امکان.
- [ ] ثبت provider/product/framework و نسخه دقیق مربوط به آموزش.
- [ ] تشخیص خودکار نسخه از URL، مستندات، عنوان، metadata یا محتوای منبع در صورت امکان.
- [ ] امکان تعیین دستی version و compatibility توسط کاربر.
- [ ] نگهداری چند نسخه از یک موضوع بدون overwrite کردن دانش قبلی.
- [ ] ایجاد رابطه بین نسخه‌های متوالی یک موضوع/روش.
- [ ] تشخیص deprecated / removed / replaced / improved / unchanged برای هر آموزش یا روش.
- [ ] تشخیص اینکه روش نسخه قدیمی در نسخه جدید همچنان قابل استفاده است یا خیر.
- [ ] تشخیص روش بهتر یا recommended approach در نسخه جدید.
- [ ] ثبت منبع رسمی برای ادعای تغییر، deprecation یا replacement.
- [ ] اعتبارسنجی دوباره knowledge قدیمی هنگام انتشار نسخه جدید.
- [ ] trigger خودکار برای re-check/relearning هنگام شناسایی release جدید.
- [ ] نمایش وضعیت سازگاری هر lesson با نسخه فعلی.
- [ ] هشدار هنگام استفاده از knowledge منسوخ یا version-mismatched.
- [ ] امکان فیلتر knowledge بر اساس نسخه، وضعیت اعتبار و تاریخ.
- [ ] امکان مقایسه روش/آموزش بین دو نسخه.
- [ ] نمایش زنجیره evolution یک روش: introduced → improved → deprecated/replaced.
- [ ] جلوگیری از حذف بی‌دلیل دانش قدیمی؛ دانش تاریخی باید حفظ شود ولی وضعیت اعتبار آن مشخص باشد.
- [ ] استفاده از version-aware knowledge در retrieval تا نسخه مناسب task انتخاب شود.
- [ ] اتصال version-aware learning به provenance، confidence و verification.
- [ ] تست regression برای جلوگیری از مخلوط‌شدن آموزش نسخه‌های ناسازگار.
- [ ] پشتیبانی از version ranges مثل >=1.5,<2.0 در مواردی که منبع چنین محدوده‌ای دارد.

- [ ] سنجش اینکه تجربه‌های جمع‌آوری‌شده واقعاً کیفیت یا سرعت taskهای بعدی را بهبود داده‌اند.

پروژه زمانی از نظر این نقشه «تکمیل‌شده» محسوب می‌شود که برای یک کاربر عادی، برای تغییر هر رفتار قابل تغییرِ سیستم، مسیر زیر وجود داشته باشد:

`Settings → انتخاب قابلیت → ایجاد/ویرایش → اعتبارسنجی → ذخیره → اعمال → تست → مشاهده نتیجه`

و برای قابلیت‌های حساس:

`Settings → تغییر → Approval → Snapshot → Apply → Health Check → Rollback در صورت خطا`

### اصل غیرقابل‌مذاکره

**اگر برای اضافه‌کردن یک LLM، provider، ابزار، منبع آموزشی، policy، workflow، integration یا رفتار قابل تنظیم مجبور شویم source code را ویرایش کنیم، audit باید آن مورد را به‌عنوان gap ثبت کند؛ مگر اینکه آن مورد ذاتاً یک قابلیت immutable و معماری‌محور باشد.**


# 26. Advanced Agent Intelligence — لایه پیشرفته قدرت، سرعت و کیفیت

> این بخش هدفش این است که My-AI با استفاده از مدل‌های موجود، بدون ساخت LLM اختصاصی و بدون فرض افزایش سخت‌افزار، از یک chatbot ساده به یک Agent قدرتمند، قابل یادگیری، قابل ارزیابی و قابل بهبود تبدیل شود. هیچ موردی صرفاً با طراحی یا وجود کد کامل محسوب نمی‌شود؛ هر بخش فقط بعد از implementation، تست، regression و verification به [x] تبدیل می‌شود.

## 26.1 چرخه هوشمند حل مسئله و Reasoning

[ ] **چرخه کامل Understand → Plan → Execute → Observe → Critique → Re-plan → Verify → Answer ایجاد شود.** Agent نباید برای همه درخواست‌ها یک مسیر ثابت داشته باشد. ابتدا باید بفهمد کاربر چه می‌خواهد، میزان پیچیدگی را تشخیص دهد، در صورت نیاز برنامه‌ریزی کند، ابزار یا مدل مناسب را انتخاب کند، نتیجه عملیات را مشاهده کند، آن را بررسی کند و اگر نتیجه مناسب نبود برنامه را اصلاح کند. برای کارهای ساده باید مسیر کوتاه و سریع و برای کارهای پیچیده مسیر چندمرحله‌ای استفاده شود.

[ ] **تشخیص پیچیدگی و توقف هوشمند اضافه شود.** Agent باید بتواند تشخیص دهد چه زمانی یک مسئله ساده است و چه زمانی به تحقیق، ابزار، reasoning یا چند مرحله verification نیاز دارد. همچنین وقتی evidence کافی به دست آمد باید بتواند زودتر متوقف شود تا زمان و هزینه بی‌دلیل مصرف نشود.

## 26.2 انتخاب هوشمند مدل‌ها و Providerها

[ ] **Dynamic Model Router ایجاد شود.** انتخاب مدل نباید بر اساس یک نام hard-coded باشد. سیستم باید با توجه به نوع کار، قابلیت مدل، کیفیت قبلی، latency، هزینه، سلامت provider و دسترس‌پذیری تصمیم بگیرد کدام مدل مناسب‌تر است.

[ ] **Routing از تجربه‌های واقعی یاد بگیرد.** نتیجه هر انتخاب مدل باید ثبت شود تا My-AI به مرور بفهمد کدام مدل برای coding، research، reasoning، translation، vision یا کارهای دیگر عملکرد بهتری دارد. این یادگیری باید version-aware باشد تا نتیجه قدیمی به‌صورت کورکورانه به مدل یا نسخه جدید تعمیم داده نشود.

[ ] **Fallback و Failover هوشمند وجود داشته باشد.** اگر provider یا مدل اصلی شکست خورد، سیستم باید طبق policy به گزینه مناسب بعدی برود و مشخص کند این شکست در چه شرایطی اتفاق افتاده است.

## 26.3 Multi-Agent و Ensemble تطبیقی

[ ] **برای کارهای سخت امکان استفاده از چند Agent تخصصی فراهم شود.** یک Agent می‌تواند مسئله را حل کند، دیگری تحقیق کند، دیگری نتیجه را نقد کند و دیگری verification انجام دهد؛ سپس یک synthesizer نتیجه‌ها را ترکیب کند.

[ ] **Multi-Agent فقط زمانی فعال شود که ارزش داشته باشد.** برای یک سؤال ساده نباید چند مدل اجرا شوند. سیستم باید بر اساس پیچیدگی، اهمیت، ریسک و budget تصمیم بگیرد single-agent کافی است یا باید به multi-agent ارتقا پیدا کند.

[ ] **اختلاف بین Agentها قابل تشخیص و مدیریت باشد.** اگر چند مسیر به نتایج متفاوت رسیدند، این اختلاف باید ثبت و بررسی شود و در صورت نیاز مرحله تحقیق یا verification بیشتری اجرا شود.

## 26.4 یادگیری از تجربه

[ ] **Experience Learning به یک بخش اصلی سیستم تبدیل شود.** هر اجرای مهم باید فقط پاسخ نهایی را ذخیره نکند؛ بلکه attempt، روش استفاده‌شده، ابزار، مدل، شرایط اجرا، نتیجه، failure، recovery و evidence را ثبت کند.

[ ] **از تجربه‌ها Lesson استخراج شود.** وقتی مشخص شد یک روش در شرایط مشخص جواب داده یا شکست خورده، سیستم باید بتواند آن را به یک تجربه قابل استفاده در آینده تبدیل کند؛ اما قبل از تبدیل شدن به دانش عمومی باید verification لازم انجام شود.

[ ] **اثر واقعی Lessonها اندازه‌گیری شود.** My-AI باید بتواند بفهمد آیا استفاده از یک lesson واقعاً باعث افزایش success rate، کاهش زمان، کاهش token یا کاهش خطا شده است یا فقط حجم memory را بیشتر کرده است.

## 26.5 یادگیری وابسته به نسخه

[ ] **هر آموزش و دانش با نسخه و زمان اعتبار آن ذخیره شود.** مثلاً اگر یک آموزش مربوط به Python 3.10، یک API نسخه 1 یا یک framework نسخه 4 است، این وابستگی باید بخشی از metadata آن باشد. صرفاً ذخیره کردن متن آموزش کافی نیست.

[ ] **نسخه دقیق منبع و در صورت امکان بازه اعتبار آن ثبت شود.** برای هر lesson یا knowledge item باید مشخص باشد مربوط به چه product، provider، framework، API، release یا revision است و از چه زمانی معتبر بوده است.

[ ] **چند نسخه از یک دانش هم‌زمان قابل نگهداری باشد.** دانش مربوط به نسخه 1 نباید با آمدن نسخه 2 حذف یا overwrite شود؛ باید تاریخچه آن باقی بماند تا Agent بتواند بفهمد قبلاً چه روشی وجود داشته و چه تغییری اتفاق افتاده است.

[ ] **رابطه بین نسخه‌های مختلف یک روش ثبت شود.** مثلاً مشخص شود روش B نسخه جدیدترِ روش A است یا B جایگزین A شده، A deprecated شده، A حذف شده، A همچنان معتبر است یا یک روش جدید فقط بهبود یافته است.

[ ] **وضعیت compatibility هر آموزش مشخص شود.** My-AI باید بتواند برای یک آموزش بگوید این روش برای نسخه فعلی قابل استفاده است، فقط برای نسخه‌های قدیمی معتبر است، برای نسخه جدید منسوخ شده، هنوز معتبر است یا باید قبل از استفاده دوباره بررسی شود.

[ ] **روش‌های بهتر در نسخه‌های جدید شناسایی شوند.** اگر تولیدکننده یک فناوری در نسخه جدید روش قبلی را کنار گذاشته و روش بهتری معرفی کرده است، این تغییر باید در knowledge ثبت شود و Agent هنگام پاسخ‌گویی یا اجرای task به روش جدید هدایت شود.

[ ] **تشخیص تغییرات تا حد امکان با منابع رسمی انجام شود.** deprecation، replacement، breaking change و recommended approach باید تا جای ممکن با مستندات رسمی، release notes، changelog یا منبع معتبر پشتیبانی شوند.

[ ] **انتشار نسخه جدید باعث re-check دانش مرتبط شود.** وقتی release جدید یک provider، framework، API یا ابزار شناسایی شد، My-AI باید بتواند دانش قبلی مرتبط را دوباره بررسی کند و موارد مشکوک یا منسوخ را مشخص کند.

[ ] **Retrieval نسخه مناسب را در اولویت قرار دهد.** هنگام پاسخ‌گویی، Agent نباید صرفاً نزدیک‌ترین متن را پیدا کند؛ باید نسخه و compatibility را نیز در نظر بگیرد تا مثلاً آموزش API نسخه 1 به سؤال مربوط به API نسخه 2 پاسخ ندهد.

[ ] **دانش قدیمی حذف نشود مگر با policy مشخص.** دانش تاریخی ارزش دارد، اما باید برچسب وضعیت داشته باشد تا Agent آن را با دانش فعلی اشتباه نگیرد.

## 26.6 Skill System پویا

[ ] **هر Skill به یک موجودیت مستقل و versioned تبدیل شود.** یک Skill باید بتواند description، prerequisite، tools، prompts، examples، tests، نسخه و سابقه موفقیت داشته باشد.

[ ] **Agent بتواند Skill مناسب را کشف و انتخاب کند.** بر اساس task، سابقه موفقیت و compatibility، Skill مناسب انتخاب شود و بعد از اجرا verification انجام شود.

[ ] **Skillهای جدید از تجربه‌ها پیشنهاد شوند ولی بدون verification فعال نشوند.** چرخه باید candidate → verify → activate → rollback باشد تا یادگیری اشتباه وارد رفتار اصلی سیستم نشود.

## 26.7 Knowledge Graph و ارتباط بین دانش

[ ] **دانش پروژه و تجربه‌ها علاوه بر متن به شکل entity و relation نیز قابل مدل‌سازی باشند.** برای مثال رابطه بین project، file، bug، commit، decision، skill، task، model و knowledge ثبت شود تا Agent بتواند روابط را دنبال کند.

[ ] **تاریخچه و زمان در Knowledge Graph لحاظ شود.** رابطه‌ای که در نسخه قبلی برقرار بوده ممکن است در نسخه جدید دیگر معتبر نباشد؛ بنابراین graph باید temporal و version-aware باشد.

## 26.8 جست‌وجوی ترکیبی و Reranking

[ ] **Retrieval فقط متکی به Vector Search نباشد.** Vector، keyword، metadata، temporal filtering، graph retrieval و در صورت نیاز reranking باید بتوانند با هم استفاده شوند.

[ ] **کیفیت Retrieval قابل اندازه‌گیری باشد.** معیارهایی مانند recall، precision و MRR یا معیار مناسب task باید مشخص کنند آیا Agent واقعاً اطلاعات درست را پیدا می‌کند یا فقط context بیشتری دریافت می‌کند.

## 26.9 Context Engineering

[ ] **Context Planner ایجاد شود.** قبل از ارسال اطلاعات به LLM، سیستم باید تصمیم بگیرد کدام memory، فایل، تجربه، دانش، ابزار و تاریخچه واقعاً برای task لازم است.

[ ] **Context compression و budget وجود داشته باشد.** اطلاعات تکراری یا کم‌ارزش حذف و اطلاعات مهم حفظ شوند تا کیفیت بالا برود و token و latency کاهش پیدا کند.

## 26.10 Verification مستقل

[ ] **Generator و Verifier تا حد امکان از هم مستقل باشند.** Agent نباید فقط به confidence خودش اعتماد کند. نتیجه باید با evidence، test، invariant یا مسیر مستقل دیگری بررسی شود.

[ ] **Verification بر اساس نوع task تغییر کند.** کد با compile/test/static analysis، تحقیق با source/citation/freshness/contradiction check و محاسبات با مسیر مستقل بررسی شوند.

[ ] **برای نتایج حساس escalation وجود داشته باشد.** اگر verification اولیه کافی نبود، سیستم باید بتواند verifier قوی‌تر یا مرحله تحقیق دیگری را فعال کند.

## 26.11 Confidence مبتنی بر Evidence

[ ] **Confidence Engine مستقل ایجاد شود.** confidence نباید فقط عددی باشد که LLM درباره پاسخ خودش اعلام کرده است؛ باید از کیفیت منابع، میزان agreement، تازگی، verification و سابقه عملکرد ساخته شود.

[ ] **Confidence روی رفتار Agent اثر بگذارد.** confidence بالا می‌تواند اجازه پاسخ مستقیم بدهد، confidence متوسط می‌تواند verification بیشتر ایجاد کند و confidence پایین می‌تواند trigger تحقیق یا درخواست اطلاعات بیشتر باشد.

## 26.12 آزمایشگاه ارزیابی Agent

[ ] **یک Agent Evaluation Lab داخلی ساخته شود.** مجموعه‌ای از taskهای واقعی پروژه ایجاد شود تا هر تغییر مهم روی آن‌ها آزمایش شود.

[ ] **کیفیت در چند محور اندازه‌گیری شود.** correctness، hallucination، tool-use، planning، retrieval، memory، coding، latency، token و cost باید جداگانه قابل اندازه‌گیری باشند.

[ ] **Regression Benchmark مستقل از unit test داشته باشیم.** سبز بودن pytest به تنهایی نباید به معنی بهتر شدن Agent باشد؛ باید مشخص شود تغییر جدید در توان واقعی سیستم regression ایجاد نکرده است.

## 26.13 Regression Intelligence و آزمایش نسخه‌ها

[ ] **قبل از هر تغییر مهم baseline ثبت شود.** نسخه جدید باید با نسخه قبلی مقایسه شود و مشخص شود کدام قابلیت بهتر یا بدتر شده است.

[ ] **A/B testing برای prompt، model، routing و retrieval در صورت مناسب بودن اضافه شود.** candidateها باید روی taskهای واقعی آزمایش شوند و فقط candidateهایی که evidence کافی دارند امکان فعال شدن داشته باشند.

[ ] **candidate ناموفق قابل rollback باشد.** هیچ بهبودی نباید صرفاً به خاطر یک نمونه موفق وارد production شود.

## 26.14 Research Agent

[ ] **Research از یک search ساده به pipeline تحقیق تبدیل شود.** سؤال باید در صورت نیاز شکسته شود، منابع متعدد بررسی شوند، evidence استخراج شود، اختلاف منابع پیدا شود و نتیجه نهایی با provenance ساخته شود.

[ ] **منبع دستی و کشف خودکار کنار هم پشتیبانی شوند.** کاربر می‌تواند URL، فایل، کتاب، repository یا مستندات بدهد و یا از My-AI بخواهد خودش منابع معتبر را پیدا کند.

[ ] **تازگی و اعتبار منبع بخشی از تصمیم باشد.** Research Agent باید بتواند تشخیص دهد یک منبع برای موضوع فعلی قدیمی است یا هنوز معتبر است.

## 26.15 Secure Computer / Environment Agent

[ ] **Agent بتواند در محیط کنترل‌شده کار واقعی انجام دهد.** filesystem، shell، Git، database، browser و سایر ابزارها در صورت فعال بودن باید sandbox، permission، timeout، resource limit و audit داشته باشند.

[ ] **تغییرات محیطی قابل snapshot و rollback باشند.** Agent باید بتواند قبل از عملیات حساس وضعیت را ثبت کند و در صورت شکست به وضعیت امن قبلی برگردد.

## 26.16 اجرای موازی

[ ] **کارهای مستقل به صورت موازی اجرا شوند.** Task باید به dependency graph تبدیل شود تا بخش‌هایی که وابستگی ندارند هم‌زمان اجرا شوند و بعد خروجی‌ها merge شوند.

[ ] **Concurrency و cancellation کنترل شوند.** parallelism نباید باعث race condition، مصرف بی‌رویه منابع یا باقی ماندن taskهای بلااستفاده شود.

## 26.17 Caching هوشمند

[ ] **نتایج قابل cache در چند سطح ذخیره شوند.** LLM response، tool result و retrieval در صورت مناسب بودن cache شوند تا درخواست‌های تکراری دوباره هزینه کامل نداشته باشند.

[ ] **Cache باید version-aware و freshness-aware باشد.** با تغییر source، configuration، model یا نسخه فناوری، cache نامعتبر باید invalidate شود و secret یا داده حساس هرگز بدون policy مناسب cache نشود.

## 26.18 بهینه‌سازی Token / Latency / Cost

[ ] **برای هر task budget مشخص شود.** تعداد token، step، tool call، زمان و هزینه باید قابل کنترل باشد و Agent بر اساس budget باقی‌مانده مسیر خود را تغییر دهد.

[ ] **Early Exit و انتخاب مسیر کم‌هزینه اضافه شود.** بخش‌های کم‌ریسک نباید به مدل یا reasoning گران سپرده شوند و کارهای ساده باید با کمترین مسیر لازم انجام شوند.

[ ] **Efficiency واقعی اندازه‌گیری شود.** برای هر task باید بتوان فهمید افزایش کیفیت با چه مقدار token، زمان و هزینه به دست آمده است.

## 26.19 Event-Driven Agent

[ ] **سیستم بتواند با Event کار کند نه فقط درخواست مستقیم کاربر.** مثلاً تغییر repository، ایجاد issue، انتشار نسخه جدید یا تغییر منبع آموزشی بتواند trigger یک workflow شود.

[ ] **Event lifecycle امن باشد.** retry، dead-letter، idempotency و audit باید برای eventهای مهم وجود داشته باشد و automation از Settings قابل فعال/غیرفعال شدن باشد.

## 26.20 Meta-Agent / Agent Optimizer

[ ] **یک لایه بالاتر برای تحلیل و بهبود خود Agent ایجاد شود.** این لایه باید بتواند bottleneckهای model، tool، memory، prompt، skill و workflow را پیدا کند و candidate برای بهبود پیشنهاد دهد.

[ ] **Meta-Agent حق تغییر مستقیم production نداشته باشد.** candidate باید در sandbox آزمایش، benchmark، verification و approval شود و سپس با snapshot و rollback قابل activation باشد.

## 26.21 Agent Operating System

[ ] **My-AI در نهایت یک Agent Operating System یکپارچه داشته باشد.** task، session، memory، tool، skill، model، policy، event، evaluation و recovery باید lifecycle و registry مشترک داشته باشند.

[ ] **تمام اجزای قابل تغییر از Settings مدیریت شوند.** API، CLI و UI باید تا حد امکان همان configuration و capability registry را مصرف کنند تا رفتار سیستم از سه مسیر متفاوت و ناسازگار مدیریت نشود.

## 26.22 تکامل تجربه در کنار نسخه‌ها

[ ] **هر Experience باید نسخه محیطی خود را داشته باشد.** وقتی Agent تجربه‌ای ثبت می‌کند باید مشخص باشد با کدام نسخه model، provider، framework، API، tool، skill و configuration اتفاق افتاده است.

[ ] **تجربه باید شرایط اجرای خود را نیز نگه دارد.** فقط «این روش جواب داد» کافی نیست؛ باید مشخص باشد چرا، کجا، با چه ورودی، چه ابزارهایی و تحت چه شرایطی جواب داده است.

[ ] **تجربه‌های قدیمی پس از تغییر نسخه دوباره اعتبارسنجی شوند.** اگر نسخه جدید منتشر شد، My-AI باید بتواند بررسی کند تجربه قدیمی هنوز معتبر است، با تغییر جزئی قابل استفاده است، deprecated شده یا روش جدیدی جای آن را گرفته است.

[ ] **تجربه‌های متناقض در کنار هم نگهداری و مقایسه شوند.** مثلاً اگر روش A در نسخه 1 موفق و در نسخه 2 ناموفق بوده و روش B در نسخه 2 موفق شده، این evolution باید به شکل قابل فهم ثبت شود.

[ ] **Lessonها به نسخه و compatibility وابسته باشند.** یک lesson نباید بدون بررسی از نسخه‌ای به نسخه دیگر منتقل شود. اگر سازگاری مشخص نیست، Agent باید آن را به عنوان دانش نیازمند verification در نظر بگیرد.

[ ] **Experience history در تصمیم‌های آینده استفاده شود.** تجربه‌های نسخه فعلی باید اولویت داشته باشند و تجربه نسخه‌های قدیمی فقط وقتی وارد تصمیم شوند که compatibility آن‌ها مشخص باشد.

[ ] **تجربه‌های اشتباه قابل invalidate شدن باشند.** کاربر یا سیستم پس از evidence جدید باید بتواند تجربه یا lesson قدیمی را با ثبت دلیل از چرخه تصمیم‌گیری خارج کند، بدون اینکه تاریخچه آن از بین برود.

[ ] **اثر Experience Learning اندازه‌گیری شود.** باید بتوانیم با benchmark نشان دهیم جمع‌آوری تجربه باعث افزایش کیفیت، کاهش failure، کاهش زمان یا کاهش هزینه شده است.
