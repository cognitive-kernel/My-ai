### 1.1 اتصال LLM اختصاصی / Custom LLM Provider

این زیر‌بخش برای زمانی است که My-AI در آینده یک LLM اختصاصی داشته باشد یا از یک سرویس مدل سفارشی استفاده کند. هدف این نیست که هسته Agent به API یک شرکت خاص وابسته شود؛ Provider باید فقط یک adapter باشد و lifecycle مدل، routing، memory، tools و evaluation مستقل از آن باقی بمانند.

**[x] مسیر Provider برای LLM سفارشیِ OpenAI-compatible در runtime ایجاد شود.** — اگر LLM اختصاصی API سازگار با OpenAI داشته باشد، می‌توان آن را بدون تغییر Agent از طریق تنظیمات به سیستم متصل کرد.

**[x] endpoint، model ID و API key مربوط به LLM سفارشی از Configuration Registry قابل تنظیم باشند.** — endpoint و model در Registry قرار می‌گیرند و API key به‌صورت secret ذخیره می‌شود و در export معمولی افشا نمی‌شود.

**[x] انتخاب Provider فعال از Configuration Registry انجام شود.** — انتخاب provider دیگر فقط به مقدار محیطی وابسته نیست و runtime می‌تواند provider سفارشی ثبت‌شده را انتخاب کند.

**[x] برای LLMهای دارای API غیر OpenAI-compatible یک Provider Adapter عمومی وجود داشته باشد.** — در این مرحله باید interface مشخصی برای chat، streaming، structured output، health-check، token usage و error mapping تعریف شود تا LLM اختصاصی با protocol دلخواه نیز بدون تغییر Agent قابل اتصال باشد.

**[x] تعریف Provider سفارشی از UI با تست اتصال، capabilities، health-check و version ثبت شود.** — کاربر باید بتواند Provider را بدون تغییر source code اضافه و مدیریت کند و قبل از فعال‌سازی، سازگاری آن با runtime بررسی شود.

**[x] مدل سفارشی در Model Catalog با capability و نسخه ثبت شود.** — context length، streaming، structured output، embedding/reasoning capability، نسخه مدل و محدودیت‌های آن باید بخشی از metadata باشند.

**[x] مهاجرت از یک Provider به LLM اختصاصی بدون تغییر workflow و Agent تضمین شود.** — تغییر Provider نباید باعث تغییر مستقیم در business logic شود و باید با regression benchmark و verification بررسی شود.

# 26. Advanced Agent Intelligence — لایه پیشرفته قدرت، سرعت و کیفیت

## 26.1 چرخه هوشمند حل مسئله و Reasoning

[x] **چرخه کامل Understand → Plan → Execute → Observe → Critique → Re-plan → Verify → Answer ایجاد شود.** Agent نباید برای همه درخواست‌ها یک مسیر ثابت داشته باشد. ابتدا باید بفهمد کاربر چه می‌خواهد، میزان پیچیدگی را تشخیص دهد، در صورت نیاز برنامه‌ریزی کند، ابزار یا مدل مناسب را انتخاب کند، نتیجه عملیات را مشاهده کند، آن را بررسی کند و اگر نتیجه مناسب نبود برنامه را اصلاح کند. برای کارهای ساده باید مسیر کوتاه و سریع و برای کارهای پیچیده مسیر چندمرحله‌ای استفاده شود.

[x] **تشخیص پیچیدگی و توقف هوشمند اضافه شود.** Agent باید بتواند تشخیص دهد چه زمانی یک مسئله ساده است و چه زمانی به تحقیق، ابزار، reasoning یا چند مرحله verification نیاز دارد. همچنین وقتی evidence کافی به دست آمد باید بتواند زودتر متوقف شود تا زمان و هزینه بی‌دلیل مصرف نشود.

[ ] **Verification بر اساس نوع task تغییر کند.** کد با compile/test/static analysis، تحقیق با source/citation/freshness/contradiction check و محاسبات با مسیر مستقل بررسی شوند.

[ ] **برای نتایج حساس escalation وجود داشته باشد.** اگر verification اولیه کافی نبود، سیستم باید بتواند verifier قوی‌تر یا مرحله تحقیق دیگری را فعال کند.

## 26.11 Confidence مبتنی بر Evidence

[ ] **Confidence روی رفتار Agent اثر بگذارد.** confidence بالا می‌تواند اجازه پاسخ مستقیم بدهد، confidence متوسط می‌تواند verification بیشتر ایجاد کند و confidence پایین می‌تواند trigger تحقیق یا درخواست اطلاعات بیشتر باشد.

## 26.15 Secure Computer / Environment Agent

[ ] **Agent بتواند در محیط کنترل‌شده کار واقعی انجام دهد.** filesystem، shell، Git، database، browser و سایر ابزارها در صورت فعال بودن باید sandbox، permission، timeout، resource limit و audit داشته باشند.

[ ] **تغییرات محیطی قابل snapshot و rollback باشند.** Agent باید بتواند قبل از عملیات حساس وضعیت را ثبت کند و در صورت شکست به وضعیت امن قبلی برگردد.

## 26.16 اجرای موازی

[ ] **کارهای مستقل به صورت موازی اجرا شوند.** Task باید به dependency graph تبدیل شود تا بخش‌هایی که وابستگی ندارند هم‌زمان اجرا شوند و بعد خروجی‌ها merge شوند.

[ ] **Concurrency و cancellation کنترل شوند.** parallelism نباید باعث race condition، مصرف بی‌رویه منابع یا باقی ماندن taskهای بلااستفاده شود.

## 26.17 Caching هوشمند

[ ] **نتایج قابل cache در چند سطح ذخیره شوند.** LLM response، tool result و retrieval در صورت مناسب بودن cache شوند تا درخواست‌های تکراری دوباره هزینه کامل نداشته باشند.

[ ] **Cache باید version-aware و freshness-aware باشد.** با تغییر source، configuration، model یا نسخه فناوری، cache نامعتبر باید invalidate شود و secret یا داده حساس هرگز بدون policy مناسب cache نشود.

## 26.18 بهینه‌سازی Token / Latency / Cost

[ ] **برای هر task budget مشخص شود.** تعداد token، step، tool call، زمان و هزینه باید قابل کنترل باشد و Agent بر اساس budget باقی‌مانده مسیر خود را تغییر دهد.

[ ] **Early Exit و انتخاب مسیر کم‌هزینه اضافه شود.** بخش‌های کم‌ریسک نباید به مدل یا reasoning گران سپرده شوند و کارهای ساده باید با کمترین مسیر لازم انجام شوند.

[ ] **Efficiency واقعی اندازه‌گیری شود.** برای هر task باید بتوان فهمید افزایش کیفیت با چه مقدار token، زمان و هزینه به دست آمده است.

## 26.19 Event-Driven Agent

[ ] **سیستم بتواند با Event کار کند نه فقط درخواست مستقیم کاربر.** مثلاً تغییر repository، ایجاد issue، انتشار نسخه جدید یا تغییر منبع آموزشی بتواند trigger یک workflow شود.

[ ] **Event lifecycle امن باشد.** retry، dead-letter، idempotency و audit باید برای eventهای مهم وجود داشته باشد و automation از Settings قابل فعال/غیرفعال شدن باشد.

## 26.22 تکامل تجربه در کنار نسخه‌ها

[ ] **هر Experience باید نسخه محیطی خود را داشته باشد.** وقتی Agent تجربه‌ای ثبت می‌کند باید مشخص باشد با کدام نسخه model، provider، framework، API، tool، skill و configuration اتفاق افتاده است.

[ ] **تجربه باید شرایط اجرای خود را نیز نگه دارد.** فقط «این روش جواب داد» کافی نیست؛ باید مشخص باشد چرا، کجا، با چه ورودی، چه ابزارهایی و تحت چه شرایطی جواب داده است.

[ ] **تجربه‌های قدیمی پس از تغییر نسخه دوباره اعتبارسنجی شوند.** اگر نسخه جدید منتشر شد، My-AI باید بتواند بررسی کند تجربه قدیمی هنوز معتبر است، با تغییر جزئی قابل استفاده است، deprecated شده یا روش جدیدی جای آن را گرفته است.

[ ] **تجربه‌های متناقض در کنار هم نگهداری و مقایسه شوند.** مثلاً اگر روش A در نسخه 1 موفق و در نسخه 2 ناموفق بوده و روش B در نسخه 2 موفق شده، این evolution باید به شکل قابل فهم ثبت شود.

[ ] **Lessonها به نسخه و compatibility وابسته باشند.** یک lesson نباید بدون بررسی از نسخه‌ای به نسخه دیگر منتقل شود. اگر سازگاری مشخص نیست، Agent باید آن را به عنوان دانش نیازمند verification در نظر بگیرد.

[ ] **Experience history در تصمیم‌های آینده استفاده شود.** تجربه‌های نسخه فعلی باید اولویت داشته باشند و تجربه نسخه‌های قدیمی فقط وقتی وارد تصمیم شوند که compatibility آن‌ها مشخص باشد.

[ ] **تجربه‌های اشتباه قابل invalidate شدن باشند.** کاربر یا سیستم پس از evidence جدید باید بتواند تجربه یا lesson قدیمی را با ثبت دلیل از چرخه تصمیم‌گیری خارج کند، بدون اینکه تاریخچه آن از بین برود.

[ ] **اثر Experience Learning اندازه‌گیری شود.** باید بتوانیم با benchmark نشان دهیم جمع‌آوری تجربه باعث افزایش کیفیت، کاهش failure، کاهش زمان یا کاهش هزینه شده است.

## 27. رابط گرافیکی و اجرای بدون دستور / GUI-First Action Layer

هدف این بخش این است که کاربر تا جای ممکن برای انجام عملیات روزمره مجبور به نوشتن command، endpoint یا متن دستور نباشد. هر قابلیت یا module که از نظر امنیت و UX بتواند یک عملیات مشخص و قابل‌فهم داشته باشد باید یک کنترل گرافیکی معادل آن داشته باشد؛ مانند دکمه شروع، توقف، فعال‌سازی، غیرفعال‌سازی، اجرا، تست اتصال، reset، retry، approve، reject، export یا مشاهده وضعیت.

این اصل فقط به Learning محدود نیست. باید به‌صورت یک قرارداد عمومی در معماری UI/Backend پیاده شود تا هر module جدید نیز هنگام اضافه شدن، actionهای گرافیکی خود را همراه با permission، confirmation، progress، result و audit ثبت کند.

**[x] GUI Action Registry مرکزی ایجاد شود.** — هر عملیات قابل انجام توسط کاربر باید یک شناسه، عنوان، توضیح، module، method، endpoint، permission، confirmation policy و وضعیت داشته باشد تا UI بتواند آن را به‌صورت استاندارد نمایش دهد.

**[x] برای هر action قابل‌امنیت، authorization و audit اجباری باشد.** — وجود دکمه نباید راهی برای دور زدن permission یا policy باشد؛ همان policy که برای API/CLI اعمال می‌شود باید برای UI نیز اعمال شود.

**[ ] برای عملیات طولانی دکمه‌های Start / Pause / Resume / Stop / Retry و نمایش progress وجود داشته باشد.** — کاربر باید بتواند lifecycle عملیات را بدون command مدیریت کند و وضعیت واقعی worker/runtime را ببیند.

**[x] برای عملیات configuration دکمه‌های Save / Reset / Import / Export و نمایش مقدار فعلی و default وجود داشته باشد.** — هر setting مهم باید علاوه بر API از UI قابل مدیریت باشد.

**[x] برای provider، model، tool و integration دکمه‌های Add / Edit / Enable / Disable / Delete / Test Connection / Health Check فراهم شود.** — مدیریت منابع نباید نیازمند تغییر فایل config یا اجرای command باشد.

**[ ] برای workflowهای حساس دکمه‌های Preview / Approve / Reject / Apply / Rollback وجود داشته باشد.** — مخصوصاً Self-Update، Self-Repair و تغییرات تولیدی باید lifecycle کامل و قابل مشاهده در UI داشته باشند.

**[ ] برای هر module یک Action Panel استاندارد با وضعیت، آخرین اجرا، خطا و نتیجه ایجاد شود.** — کاربر باید بدون ورود به log یا command بتواند بفهمد عملیات چه وضعیتی دارد.

**[ ] قابلیت‌های جدید بدون action گرافیکی معادل، مگر با دلیل فنی/امنیتی مستند، وارد production نشوند.** — این معیار بخشی از Definition of Done قابلیت‌های جدید باشد.

**[ ] UI Action Registry و کنترل‌های گرافیکی با تست integration و regression پوشش داده شوند.** — باید ثابت شود action از UI تا endpoint و persistence/runtime به‌درستی اجرا می‌شود و permissionها حفظ می‌شوند.
