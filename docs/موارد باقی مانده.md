# موارد باقی مانده

`Verification final قبلی فقط برای backlog قبلی معتبر است. این بخش جدید نتیجه audit مستقل کل پروژه است.`

> قانون اصلی: هیچ موردی تا زمانی که implementation، تست، regression و verification آن به‌صورت کامل انجام نشده و معیار 100٪ را نگذرانده است، نباید حذف یا تیک زده شود.

## وضعیت کلی

Backlog قبلی ۱۲ بخش داشت و معیارهای تعریف‌شده آن‌ها تکمیل شده بود. در audit مستقل جدید، چند gap فراتر از checkboxهای قبلی شناسایی شد. این موارد به‌عنوان backlog جدید اضافه شده‌اند و تا اثبات 100٪ باید باقی بمانند.

## P0 — موارد جدید شناسایی‌شده در audit کامل پروژه

### 13. Model Management — Health / Availability / Failover واقعی
وضعیت: 70٪ — implementation و تست‌های اصلی انجام شده؛ verification تکمیلی باقی است

- [x] inventory کامل provider/modelهای قابل استفاده.
- [x] health check واقعی برای هر model/provider.
- [x] تشخیص unavailable شدن مدل قبل و حین inference.
- [x] failover واقعی و قابل مشاهده به fallback model.
- [ ] timeout و retry policy مستقل برای model inference.
- [ ] جلوگیری از retry بی‌نهایت.
- [ ] ثبت model انتخاب‌شده، علت انتخاب، failure و fallback در telemetry/audit.
- [x] تست نبودن model اصلی.
- [x] تست failure هنگام inference.
- [ ] تست chain چندمرحله‌ای fallback.
- [ ] تست حفظ context هنگام fallback.
- [x] regression برای coding، chat، routing و embedding.
- [x] E2E test با provider/model واقعی یا controlled failure واقعی.

**معیار 100٪:** هر مسیر انتخاب مدل، failure و fallback در محیط تست قابل اجرا، قابل مشاهده و regression-tested باشد.

### 14. Self-Update / Self-Repair — چرخه کامل Production-Safe
وضعیت: 0٪ — نیازمند تکمیل و اثبات مجدد

- [ ] inspect و diagnose واقعی.
- [ ] تولید proposal قابل بررسی.
- [ ] approval صریح قبل از mutation.
- [ ] snapshot قبل از mutation.
- [ ] isolated worktree برای candidate.
- [ ] compile و test کامل candidate.
- [ ] activation کنترل‌شده.
- [ ] health check بعد از activation.
- [ ] rollback خودکار در failure بعد از activation.
- [ ] restore واقعی snapshot.
- [ ] rollback Git state.
- [ ] ثبت failure lesson.
- [ ] اثبات اینکه failure candidate به production state آسیب نمی‌زند.
- [ ] regression suite مستقل برای کل چرخه.
- [ ] E2E test شامل success و failure بعد از activation.

**معیار 100٪:** کل چرخه inspect → diagnose → approval → snapshot → isolated change → test → activation → health-check → rollback/restore → failure lesson به‌صورت واقعی و تکرارپذیر تست شده باشد.

### 15. Authorization — پوشش کامل Capabilityهای حساس
وضعیت: 0٪ — audit مجدد لازم است

- [ ] اثبات deny-by-default برای هر capability حساس.
- [ ] policy مستقل برای read/write/execute/system operations.
- [ ] actor/tool/action/time/request-id در auditهای لازم.
- [ ] ثبت success و failure بدون افشای secret.
- [ ] تست cross-user access.
- [ ] تست admin-only operations.
- [ ] تست bypassهای مستقیم API/tool.
- [ ] regression suite کامل authorization.

**معیار 100٪:** هیچ مسیر حساس بدون policy و audit مناسب باقی نماند و تمام مسیرهای bypass شناخته‌شده تست و مسدود شده باشند.

### 16. Skill Engine — Lifecycle کامل Verification / Revalidation / Learning

- [ ] evidence معتبر/نامعتبر/منقضی.
- [ ] version mismatch.
- [ ] revalidation واقعی.
- [ ] sandbox failure.

- [ ] score thresholdهای versioned و مستند.

- [ ] تست اینکه failure باعث downgrade/revalidation مناسب شود.

**معیار 100٪:** lifecycle کامل skill از ثبت تا verification، تغییر، invalidation، revalidation و regression با dataset واقعی پوشش داده شود.

### 17. Streaming / Session / Backup — Lifecycle و Compatibility
وضعیت: 0٪ — audit تکمیلی لازم است

- [ ] lifecycle کامل session از ایجاد تا پایان/expiry.
- [ ] recovery session پس از restart.
- [ ] streaming interruption و reconnect.

- [ ] backup/restore کامل state مرتبط با session.

- [ ] migration تست‌شده بین schema versionها.
- [ ] integrity verification پس از restore.

**معیار 100٪:** session، stream و backup در restart/crash/version migration بدون از دست رفتن state مورد انتظار رفتار تعریف‌شده را حفظ کنند.

## P1 — موارد کیفی که باید در audit جدید بررسی شوند

### 21. Silent Failure / Exception Handling Audit
وضعیت: 0٪ — شروع نشده

- [ ] inventory تمام `except: pass` و exceptionهای silently swallowed.
- [ ] تعیین اینکه هر مورد intentional است یا bug-risk.
- [ ] تبدیل failureهای مهم به logging/telemetry/audit مناسب.
- [ ] جلوگیری از پنهان شدن خطاهای امنیتی، persistence و self-repair.
- [ ] تست failure pathهای اصلاح‌شده.

**معیار 100٪:** هیچ failure مهمی بدون رفتار آگاهانه، قابل مشاهده و مستند باقی نماند.

### 22. End-to-End Architecture Audit
وضعیت: 0٪ — شروع نشده

- [ ] تطبیق مستندات معماری با implementation واقعی.
- [ ] inventory APIهای public و internal.
- [ ] بررسی dependency boundary بین modules.
- [ ] بررسی configuration و environment variables.
- [ ] بررسی startup/shutdown lifecycle.
- [ ] بررسی error propagation بین لایه‌ها.
- [ ] تست E2E مسیر اصلی user request → routing → tool/knowledge → response.
- [ ] ثبت gapهای جدید در همین فایل.

**معیار 100٪:** هر قابلیت اصلی پروژه از ورودی تا خروجی واقعی قابل ردیابی، تست و مستند باشد و gap ناشناخته‌ای در boundaryهای اصلی باقی نماند.

## قانون چرخه تکمیل

برای هر مورد:

1. implementation کامل شود.
2. تست‌های همان مورد اجرا شوند.
3. هر failure اصلاح شود.
4. تست مجدد اجرا شود.
5. regression مربوط به بخش اجرا شود.
6. در صورت سبز بودن همه موارد، وضعیت به `100٪ — تکمیل شده` و checkboxها به `[x]` تغییر کنند.
7. سپس مورد بعدی شروع شود.

**هیچ موردی صرفاً به دلیل وجود implementation یا پاس شدن یک تست حذف یا تیک زده نمی‌شود.**
